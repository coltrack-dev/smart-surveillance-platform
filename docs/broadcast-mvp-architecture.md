# Broadcast MVP architecture investigation

## Findings and decisions

- **Camera API/data:** `camera-service` owns persistent `cameras` records and credential decryption. Its internal connection endpoint returns the camera ID, RTSP URL and processing mode to `stream-service`; passwords are omitted from ordinary camera responses. Broadcast stores only the camera ID and never copies camera credentials.
- **Stream API/data:** `stream-service` exposes `/api/streams/{cameraId}/start`, `stop`, and status. `StreamManager` keeps one runtime session per camera ID. Its synchronized `start` returns the current session when an ingest worker already owns that camera; its ingest-agent client also reconciles a duplicate start against the existing camera pipeline. Broadcast therefore calls this lifecycle rather than creating FFmpeg or agent jobs of its own.
- **MediaMTX and agent:** the Rust agent accepts Bearer-authenticated pipeline management calls, validates RTSP URLs, and runs FFmpeg. It publishes to the camera UUID RTSP path in MediaMTX. Streaming MediaMTX has distinct publish-only and read-only internal users configured with its supported `MTX_AUTHINTERNALUSERS_*` environment overrides ([configuration](https://mediamtx.org/docs/features/configuration), [authentication](https://mediamtx.org/docs/features/authentication)). The agent publish credential stays server-side. HLS reads are proxied by `stream-service` using the read credential; clients never receive MediaMTX credentials or direct MediaMTX URLs.
- **Existing HLS:** the existing gateway `/media-hls/**` route is a direct MediaMTX proxy. It is not suitable for public broadcast playback. A new `stream-service` playback proxy will validate a short-lived HMAC-signed token for the playlist and every segment/key request, then authenticate to MediaMTX internally. Rewritten playlist references carry the same token. Disabling/deleting a broadcast invalidates its playback immediately.
- **Ownership and cleanup:** broadcasts are associated with a camera/stream ID. On enable, `StreamManager.start` reuses a live session or creates the one session if none exists. The Broadcast row records whether this operation created the session. Disable/delete only stop a stream owned by that broadcast; a pre-existing surveillance stream remains running. This MVP assumes one `stream-service` instance, matching the current Compose topology.
- **Placement:** no `broadcast-service` is needed for this MVP. Putting broadcast management in `stream-service` avoids a service-to-service lifecycle race and extra container while reusing the existing stream lifecycle. Move the control plane only if multi-tenant billing, distributed media-node scheduling, or independent scaling justify the boundary.
- **Persistence:** existing `StreamSession` state is intentionally in-memory and no persistent Stream entity exists. A small `broadcasts` table in the existing PostgreSQL database stores ID, camera ID, enabled state, stream ownership, and timestamps. A new stream-service Flyway history/table is isolated from camera/recording migrations; no existing schema is altered.
- **Auth boundary:** current gateway and Camera/Stream management APIs do not authenticate users. The new Broadcast management routes require a dedicated Bearer management secret. Playback uses a separate short-lived signed token. This is service-token authentication for a single-operator MVP, not user identity or tenant authorization. Keep the streaming gateway on loopback/private ingress; the broader existing surveillance API surface is not made public-safe by this change.
- **Limits:** streaming HLS and management requests receive bounded in-memory rate limits, and the HLS proxy caps concurrent upstream reads at 32. The Rust agent also limits concurrent probes and active pipelines. These are basic single-instance safeguards, not distributed quotas. MediaMTX, Kafka, and ingest-agent ports remain private in streaming Compose. No MediaMTX API is enabled or routed.

## Migration / operational requirements

`stream-service` now needs the same PostgreSQL host/database credentials already used by Camera and Recording. Flyway creates only its own broadcast table and history. A production rollout must confirm the schema is backed up and the DB user can create the migration table. New playback signing and management secrets must be long random values and stable across restarts; changing the signing secret invalidates issued links. The demo Compose retains its existing behavior and gains the same DB variables for stream-service.

This phase does not introduce tenant IDs, subscriptions, user authentication, billing, CDN signing, shared/distributed rate limits, or HA ownership locks. Those remain SaaS launch requirements.
